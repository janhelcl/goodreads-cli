# Live CLI UAT — 2026-09-22

Sanitized user-acceptance run of the public `gr` command surface. This is
observation, not a compatibility promise. It does not contain titles, authors,
book IDs, owner ISBNs, review text, profile paths, cookies, or CSV row contents.

Related evidence: [compatibility-matrix.md](compatibility-matrix.md).
Previous public-CLI run: [uat-2026-09-20.md](uat-2026-09-20.md).

## Setup

| Item | Value |
|---|---|
| Date | 2026-09-22 |
| Binary | local `gr dev` built from `main` `a55add3` |
| Platform | Linux x86-64 |
| Browser | Google Chrome 143.0.7499.40 |
| Session | `gr logout`, then fresh interactive `gr login --json` |
| Display | `DISPLAY=:0` |

The owner library still had three rows: two exact-ISBN editions and one owner
row that renders neither ISBN-10 nor ISBN-13. `currently-reading` was empty.
Both exact editions were `read` with unset finish dates; one was rated 5 and
one was unrated. The spec-example edition `9781603580557` was absent.

## Verdict

Logout, fresh headed login, existing-session login, reads, rate, review,
`start` then `add --shelf read`, public `finish --date` for a non-today day,
export, MCP, validation, locking, and debug redaction worked on this machine.

Two functional problems showed up on this run:

1. During interactive login, a second tab to the private library opened and
   closed rapidly whenever the sign-in URL was not exactly `/user/sign_in`.
2. Public `gr add` of a known-absent exact ISBN returned `book_not_found` in
   about three seconds. A liveprobe that waits for a `/book/show/` search
   result found that edition on the same session. Later: search wait,
   JSON-LD identity, and the Want-to-Read settle wait unblocked a
   reversible add canary of that ISBN; the public CLI `add` was not
   re-run.

A leftover headless Chrome from a failed command also blocked later launches
until the CLI-owned profile process was killed.

## Passed

### Usage and validation

Local argument checks (no browser) accepted help, `--version`, and shell
completion. Invalid usage returned exit 2 with empty stdout, including:

- extra positional arguments on no-arg commands
- negative `--timeout`
- unknown flags
- invalid shelves, ratings, limits, and dates (including `2026-02-29` and
  unpadded `2026-9-17`)
- invalid or checksum-failing ISBNs, titles used as ISBNs, empty ISBN
- `review` without exactly one of `--text` / `--file` / `--clear`; empty or
  whitespace `--text`; missing `--file`; combining those flags
- `export --json` without `--out`; `--force` without `--out`; existing file
  without `--force`; directory, symlink, and missing-parent destinations
- `mcp` with extra arguments
- `gr foobar`, `gr --debug foobar`, and `gr --json foobar` (exit 2,
  `unknown command "foobar"`, `--debug` `error_kind=invalid_arguments`)

`--json` on failures stayed on stderr as human text.

### Authentication

- Pre-logout `status --json` was connected / `session_valid` in about two
  seconds. `--debug` named Chrome 143.0.7499.40 and stayed redacted.
- `logout --json` returned `{"connected":false,"profile_removed":true}` and
  removed the dedicated profile. Repeat `logout --json` and `gr --json logout`
  were idempotent.
- After logout, `status` was disconnected (`session_valid` false) without
  launching a browser. `library` and `get` returned exit 3
  (`Goodreads session expired; run gr login.`) with empty stdout.
- Fresh `login --json --debug` opened a headed Chrome window. After manual
  sign-in it returned `{"connected":true,"session_valid":true}` in about 157
  seconds. Debug: `stage=login.complete`, Chrome 143.0.7499.40, `error_kind=none`.
- A new process `status --json` and `gr --json --no-color status` both
  reported connected. Persistent flags worked before the subcommand.
- Existing-session `login --json` returned connected in about two seconds
  without another sign-in. It still printed
  `Opening Goodreads in a dedicated browser. Complete sign-in there.`

### Library and get

- Unfiltered `library` returned the three owner rows as compact JSON and as
  human `Title — Author (status)` lines. JSON includes `average_rating` and
  `date_added`; `review` is omitted because these reads parse the shelf table.
- `--shelf to-read` (one unidentified row), `--shelf read` (two exact
  editions), `--rating 5`, `--rating 4` (empty), `--shelf read --rating 5`,
  `--limit 1`, and empty human `No books found` behaved as specified. Empty
  JSON shelves were `[]`.
- Empty `currently-reading` returned `[]` / `No books found` in about two
  seconds (CLI and later MCP).
- `get` accepted ISBN-13, ISBN-10, and hyphenated forms of a present exact
  edition in two to four seconds. Spaced input of the same ISBN succeeded
  but took about 63 seconds; a later public retry of that spaced form
  returned in about two seconds.
- A valid ISBN not in the library returned exit 4 in about three seconds.
- `get` of a plausible public ISBN that is not the unidentified owner row
  returned exit 4 in about three seconds.

### Process behavior

- `status --timeout 1ms --json --debug` three times: exit 6, empty stdout,

- `GOODREADS_CLI_BROWSER` pointing at a missing executable: exit 9. A later

## Failed or flaky

### Interactive login opens a flashing library tab

`Login` first calls `Status`, which opens `/review/list` in a new tab and
closes it. While waiting for sign-in it calls `Status` again whenever the
visible URL is a Goodreads page whose path is not `/user/sign_in`, including
on every URL change (up to twice a second). Amazon/Goodreads sign-in uses
paths such as `/ap/signin`, so a second tab to the private library opened
and closed rapidly during the user-controlled flow.

Login still succeeded after manual sign-in. The extra tab is a UX defect
and can steal focus. If `Status` ever hits an unexpected mid-auth page, the
same loop can abort the whole login.

### Public `add` of a known-absent exact ISBN — `book_not_found`

Two public `gr add` attempts of previously absent `9781603580557`
(hyphenated, then bare ISBN-13) returned exit 4 in about 3.4s and 2.5s with
`error_kind=book_not_found`. No owner row was created.

A live `addprobe` on the same session, which waits until at least one
`/book/show/` search link exists, found one unique book route and both
ISBN-10 and ISBN-13 on the search page, then reached the book page with a
Want-to-Read control.

Public resolve now waits only for `form[action='/search']`, then treats zero
`/book/show/` links as not-found. That is too early for a live search that
still hydrates results after the form is present. The throwaway edition was
not added and did not need restoration.

Later: public resolve waits for a `/book/show/` result or
`.NoBookSearchResults`. Live search on this session showed the form about
100ms before the first book route; a nonsense query then rendered the empty
marker. The book page did not put either ISBN in the visible metadata
section, so identity uses the `Book` JSON-LD `isbn`. A later
`get 9781603580557` returned `book_not_found` in about 4.6 seconds after
proving that public edition. Add also waits for Want to Read to leave the
add state before closing the book page. A reversible canary then added the
edition, verified the owner row, and restored the original absence in about
27 seconds. The library still has the original three rows.

### Leftover Chrome after a failed command

The first public `finish --date` on a present exact edition returned exit 4
`book_not_found` in about 2.3s. The next `get` returned a network error;
later `status` / `get` returned exit 3 (`Could not launch the dedicated
browser`) because a headless Chrome was still using the CLI profile. After
that process was killed, `status` was connected, `library` still had the
three owner rows, and `get` of the same edition succeeded. A retry of
`finish --date` then verified.

Treat leftover profile Chrome as a launch blocker, and treat a very fast
`book_not_found` on a just-read edition as flaky when the profile is
contended.

Later: Close sends `Browser.close` on an independent timeout, then
stops leftover processes whose command line uses the exact dedicated
`--user-data-dir`. Launch, while holding the profile lock, does the
same sweep before starting Chrome. A local leftover Chrome started
against a temp profile no longer blocks the next launch; a suffix
profile path is left alone. Public `finish` was not re-run.

### Spaced ISBN `get` was slow

Spaced input of a present exact ISBN succeeded, but took about 63 seconds
versus two to four seconds for ISBN-13, ISBN-10, and hyphenated forms of
the same edition.

Later: spaced input is normalized before any browser work, so it is the
same ISBN-13 as the compact form. The slow path is an owner table that
paints `#books` before ISBN cells hydrate: every row looks unidentified
and `get` falls through to public search. Exact resolution now keeps
reading that page until an ISBN appears or the empty column is stable.
A local fixture that hid both ISBNs for the first three DOM reads, then
revealed them, resolved the owner row without opening `/search`. A later
public `get` of the same present edition with spaced grouping returned
in about two seconds, matching compact and hyphenated forms on this
session.

## Account state after the run

Session remained connected. The dedicated profile was recreated by the
fresh login and was not removed at the end.

The three owner rows match the start of the run: unidentified `to-read`
row untouched; two exact-ISBN `read` rows with the original ratings and
unset finish dates. The spec-example edition was still absent. No leftover
CLI profile Chrome was running after the final status check.

## Not covered

- `--headed` on commands other than `login`
- macOS / Windows
- Rod-managed Chromium download
- a library larger than one shelf page
- MCP `add_book` / `start_reading` / `finish_reading` / `review_book` writes
- public CLI `add` of a new edition after the search-wait failure
  (a reversible `addcanary` of the same ISBN passed)

## Follow-up

- Login should not open a disposable `/review/list` tab on every poll.
  Detect success from the sign-in tab, or reuse one hidden status page.
- Public ISBN search now waits for a `/book/show/` result or
  `.NoBookSearchResults`. Edition proof uses visible metadata or JSON-LD.
  Add waits for Want to Read to leave the add state before closing the
  book page. A reversible canary added and restored the spec-example
  edition after those changes.
- Closing the dedicated browser after failure now stops leftover
  processes that still use the exact dedicated `--user-data-dir`. Launch
  does the same sweep before starting Chrome, so a leaked profile Chrome
  is not a launch blocker. Public `finish` was not re-run.
- Spaced ISBN `get` is the same normalized edition as compact input.
  Exact resolution now waits for hydrating ISBN cells so a present owner
  row is not sent through public search. A later public spaced `get` of
  the same present edition returned in about two seconds.
